## 0. 先划边界：哪些是你做的，哪些是 AI 写的

**这是最大的风险点。** 面试官问「这个项目你负责哪部分」时，答案必须干净。

代码里有明确的自证痕迹：文件头 docstring 写着「移植自 xiaob」「移植自 yaya backend」——
这说明**记忆树是从你自己的另一个项目 xiaob 搬过来的**，这是可以理直气壮讲的：

```
memory/sqlite_memory_tree.py  ← 移植自你自己的 xiaob 项目（同一套设计）
agent.py                      ← docstring 明写「移植自 yaya backend agent.py」
```

所以你的叙事应该是：**「核心技术我在另一个项目里做过，这个项目是把它产品化到桌面场景」**，
而不是「我独立设计了这套架构」。前者站得住，后者一追就穿。

## 2. 最硬的技术点：分层摘要记忆树

### 2.1 为什么不能简单截断 / RAG

**问：上下文超了，直接截断不行吗？**
> 行，但会丢最早的对话，而早期对话往往定义了人物设定和长期目标。
> RAG 是检索式的，但对话有强时序因果——第 50 轮的回答依赖第 3 轮的前提，
> 单纯按相似度检索会捞到语义像但因果无关的片段。
> 我要的是**按时间推进的分层归纳**：越老的信息越粗，越近的信息越细。

### 2.2 阈值 20 / 10 万 / 8 / 4 是怎么来的（⚠️ 高频追问）

代码事实（`middleware.py`）：
```python
SUMMARIZE_KEEP_MESSAGES   = 20       # 保留最近 20 条原文不动
SUMMARIZE_TOKEN_BUDGET    = 100000   # 叶子压缩：原始消息估算 token ≥ 10 万触发（唯一触发条件）
LEVEL_COMPACT_THRESHOLD   = 8        # 同层活跃节点 ≥8 → 向上合并（节点合并仍按条数）
BRANCHING_FACTOR          = 4        # 取最早的 4 个合并成 1 个父节点
```

**答法（关键：讲清取舍，不要讲「我试了很多次」这种模糊话）**：
> 「叶子触发用 **token 预算**而不是条数：条数和上下文占用的关系太不稳定——一句寒暄和一段
> 工具输出可能差三个数量级；写代码场景几十条消息就能顶到十几万 token。按估算 token（字符 × 1.2）
> 触发，聊天和大输出两种情况都统一。留 20 条原文是让模型仍能精确回看最近几轮，
> 超过 20 轮前的内容靠摘要已经够用（连 20 条都超预算时只保留最后 1 条，避免卡死）。
> **8 和 4 是同一个数推的**（节点合并仍按条数）：8 个节点触发、4 合 1，意味着合并后剩 4 个、
> 下轮再攒到 8 个又合，压缩比恒定 2:1，不会出现某次合并把信息压得过碎。
> 而且这四个值**全部暴露在设置页**（`compress_token_budget`/`compress_keep`/`compact_threshold`/`compact_factor`），
> 用户能自己调——因为不同对话密度差异很大。」

**深挖一层（如果继续追问）**：
> 「为什么不写死？因为踩过坑。早期版本门槛写死 60 条，设置页调了不生效——
> 于是我改成全部读 settings。后来发现条数口径本身不合适（密集工具调用时 60 条早就爆了上下文），
> 干脆把叶子触发换成 token 预算一项，设置页也同步删掉了『触发条数』，避免出现两个看似都生效、
> 实际只有一个起作用的旋钮。教训是**配置项必须真的驱动执行路径，且口径要唯一**。」

⚠️ **注意**：`memory/sqlite_memory_tree.py:21` 有个 `LEAF_SIZE = 20` 常量，**全项目零引用**，
真正生效的是 `middleware.py` 里的 `SUMMARIZE_KEEP_MESSAGES`。被问到别当成两个阈值答。

### 2.3 异步压缩（工程含量最高的一段）

**问：压缩要调 LLM，要 10~30 秒，不就把对话卡死了？**

> 对，第一版就是在 `before_model` 里同步压缩，用户等 30 秒不能说话——这是最致命的体验问题。
> 后来拆成三段（`session.py:758-826`）：
> ① **调度线程**只做阈值检查，够 60 条就 spawn 一个后台线程，立刻返回；
> ② 后台线程对 **buffer 快照** 压缩，全程不碰真实 buffer，所以用户该聊照样聊；
> ③ 压完不是直接写回，而是**等空闲窗口**——轮询 `not _generating and not pending_response and not _inbox`，
> 空闲后做毫秒级原子替换：按消息 id 删旧 → 插节点消息 → 重排序 → 落盘 → 推 `memory_update` 事件。

**深挖一层（这是加分题，讲了说明你懂并发）**：
> 「替换为什么用**消息 id 集合**而不是下标？因为压缩要 10~30 秒，这期间用户又发了 5 条消息。
> 如果按下标算，位置全错位。用 id 精确删，新消息 id 不在删除集里自然保留。
> 还有一个防御：替换完调 `_strip_orphan_tool_messages()`——
> 因为压缩切段可能把 `ai(tool_calls)` 和它的 tool 结果切开了，留下孤儿 ToolMessage，
> DeepSeek 会直接 400。」

**再深一层（如果面试官真的追问并发）**：
> 「等待空闲用的是 0.2 秒轮询而不是 Condition，因为空闲窗口只有几十到几百毫秒，轮询足够，
> 且要能被 `_closing` 打断。真正的并发安全靠 `buffer_lock`（RLock）
> 保护 `recent_buffer`/`_inbox`，注意锁的粒度：压缩全程不持锁，只有最终替换那一小段持锁。」

### 2.4 压缩输入边界：为什么「未来信息」不发给压缩模型

**问：摘要的时候，后面的消息还没发生，你怎么知道该总结什么？**

> 早期版本确实把完整 buffer 快照发进压缩请求，让模型能看到"未来"消息，
> 再把事后澄清写进 `future_notes`。后来**改掉了**：压缩输入 = 系统角色卡 + **待压缩区原文** + 指令，
> 保留的尾部原始消息**不进压缩输入**。
> 原因有三：① 快照+指令里再嵌一遍待压缩区，同一段内容发两遍，代码场景（大工具输出）浪费极大；
> ② "未来信息"让模型的输出范围变得可争议——它可能把未来内容混进摘要；
> ③ 我们改用"保护标记"机制后，模型只需要认一种信号：没有 `[已压缩 · 不需要压缩]` 标记的
> 原始对话就是要压的目标，尾部干脆不出现，零歧义。

**深挖**：不加未来怎么保证摘要质量？
> 两层兜底：叶子上层用父节点归并时会把"后续变化"体现在更新的 `task/decisions` 里
> （覆盖/累积语义）；真要事后修正，节点还有 `explore_memory_tree` 可下钻原文。

### 2.5 压缩模型与缓存（成本敏感，加分）

> 压缩调用**与主对话同一个模型**（不引入额外配置），但走独立调用，不污染主会话上下文。
> 输入里既有节点又有原文时**不再重复发送待压缩区**（早期版本指令内还会嵌一份原文，v2 已删）。
> 成本控制主要靠：**稀有触发**（token 预算）+ **节点预算**（整节点 ~1000 token，超出软裁剪）
> + 压缩调用频率天生低。前缀缓存对压缩调用的收益不再是设计目标——
> 主对话每轮前缀稳定（节点追加为主、不重排）才是要保的缓存。

## 3. 三端架构（第二个高频问题）

**问：为什么有 Python、Electron、Android 三套？**

> 按「谁承担什么」分的，不是按「语言偏好」：
> - **Python 后端 = 唯一的大脑**。LLM 编排、记忆树、日历、本地语音模型（TTS/ASR/OCR）都在这，因为这些生态只有 Python 成熟。
> - **Electron = 桌面外壳**。悬浮球、托盘、窗口变形这些 UI 交互，网页技术做最快。
> - **Android = 独立重写，不是移植**。手机上不能跑常驻 Python 进程，所以用 Kotlin + Room 重写了记忆树和 Agent 循环。
>
> 旧数据靠 `scripts/export_to_android.py` 一次性导出成 `planner-export.json`，之后两端独立演进。

**深挖（面试官很可能问「怎么保证两端一致」）**：
> 不追求逐行一致，靠**工具契约 + 提示词对齐**，并且有 `check_android_prompt.py` 做交叉校验：
> prompt 里承诺了但代码没注册工具、代码注册了但 prompt 没提，**都会报红**。
> 逻辑核心（记忆树压缩算法）在两端各有一份实现，这是**有意识的取舍**——
> 跨端复用同一份 Python 在移动端不可行，宁可接受小范围重复，也不要引入跨进程通信。
> 如果要说得更诚实：这是维护成本，短期内用一致性校验压住，长期可能会把算法描述抽成一份共享 spec。

## 4. 会被问穿的题（提前想好，别临场编）

### Q1「压缩掉的信息玩家再也找不回来，怎么防丢？」
> 防丢有三层：① `details` 存了**原始消息全文**（不是只有摘要），节点可以展开看原文；
> ② `explore_memory_tree` 工具让模型按需回溯任意层级的节点摘要；
> ③ 我用 LoCoMo 做了量化评测——138 条真实长对话，`llm_score 0.688`，这是「摘要后还能答对多少」的实测值，
> 不是拍脑袋。
> **诚实补充**：原文虽然存着，但模型不会主动去翻，召回率依赖提示词引导，这是目前的短板。

### Q2「为什么不用 LangGraph 自带的 checkpointer / 现成记忆库？」
> `agent.py` 的 docstring 里记了这个决策：**不使用 checkpointer**。
> 因为 DeepSeek 严格校验「`assistant(tool_calls)` 必须紧跟对应 tool 消息」，
> 而 checkpointer 的 `add_messages` 合并会保留中断时半写的孤儿 assistant → 直接 400（yaya 项目实测踩过）。
> 持久化我用自己的 `save_buffer_state`（messages 转 json 存 SQLite），语义更可控。

### Q3「为什么自己写中间件链，不用现成框架的？」
> 用的是 LangChain 官方的 `AgentMiddleware` 基类，10 个业务中间件是自己实现的，
> 但**所有『提前结束回合』的跳转必须在 `before_model`**——这是踩出来的铁律：
> create_agent 循环是 `model → tools → model`，在 `after_model` 跳会跳过刚返回的 tool_calls，
> 产生孤儿 `assistant(tool_calls)` → 400。

### Q4「并发怎么处理的？」
> 两把锁：`chat_lock`（同一时刻只有一条生成）+ `buffer_lock`（RLock，保护 buffer/inbox/状态）。
> 生成期间用户新消息进 `_inbox` 暂存，`PlayerPriorityMiddleware` 在 `before_model` 检测到 `_inbox` 非空就跳 end，
> **让用户消息先被处理**。生成结束在 `finally` 里消费 `_inbox` 并入 buffer，置 `pending_response` 触发下一轮。

### Q5「成本怎么控？」
> ① 图片以 `image_url` 块常驻 buffer（每张 ≤384 token），每轮重发计费 → 所以视觉可判定时每张压到 384；
> ② 压缩请求靠 prompt caching 命中前缀；
> ③ 默认模型是 `deepseek-flash`（DeepSeek-V4.1-Flash，官方 API 名；不是 pro）；
> ④ 自主学习时（心跳中调了搜索/读文件）文字照常显示但**不朗读**，避免打扰同时省 TTS。

### ❌ 不要主动提的
- 「这个项目 DAU 多少」——个人项目，没有 DAU。
- `LEAF_SIZE` 死常量（问到了就说是遗留，实际生效的是 KEEP=20）。
- 把「移植自 xiaob/yaya」说成「我独立设计」——一查 docstring 就穿。
- 单测 233 个 ✅ 这个可以讲，很扎实（`tests/` 23 个文件，覆盖记忆树/日历/并发/导出契约）。
